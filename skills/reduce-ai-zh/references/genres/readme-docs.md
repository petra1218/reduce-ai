# 文体：README / 发布说明 / 使用文档

开源文档的机器腔和论文不同：论文是学术膨胀，文档是营销装饰。两类病灶都来自模板化，但表现不一样，这里按文档实际场景处理。

## 排版

- 标题不带 emoji。一个都不带。"🚀 快速开始""✨ 特性"这套是生成式文档的标志，中文文档里尤其别扭。
- badge 最多一行：仓库托管平台、许可证，够用即止。CI 状态、下载量之类的徽章，项目真的需要再挂。
- 不给术语随手加粗。加粗一多，哪里都不可 emphasized。
- 章节按这份文档的实际需要设，不照搬"简介/特性/安装/使用/路线图/贡献/许可证"全家桶。一个安装说明只出现一次。

## 语气

陈述事实，不做营销。

> 前：一个强大而优雅的工具，能让你轻松实现惊人的效率提升！
> 后：这个脚本把 X 的构建时间从约 4 分钟压到 40 秒（数字来自实测；没实测就写"更快"，不写具体数字）。

- "强大的""高效""优雅""轻松""只需三步"——这些词删掉之后句子信息量不受损，删。
- 性能、覆盖率、规模数字必须有出处。没跑过基准就不写基准。
- 不设"为什么选择 X？"这种自问自答标题。用户为什么选，让事实说话。

## 内容纪律

- 安装步骤、配置项、命令，写一遍，写对。命令块逐字可复制执行，不为了简洁砍掉必要参数，也不为了详尽复读三遍。
- 已知问题就写已知问题，不写"仍在积极开发中"糊过去。
- 路线图要么写一两条具体的，要么不写。十五项打勾清单在 v1.0 之后没人更新，只会变成谎言。
- 版本号、文件体积、兼容范围这类数字，写之前核对，前后一致。

## 中文技术文档的语感

直接、可执行、少形容词。一句一行命令，一段一个意图。"您可以执行以下命令来安装"不如"安装："加命令块。读者是来办事的，挡在他和命令之间的每个字都要有理由。
